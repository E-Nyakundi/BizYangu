# C10 — Pack-to-unit selling: sale-flow integration

Build-order item 6's second half (models + API were already done): a sale
can now actually be rung up against a specific sellable form of a product
(a stick instead of the pack, a gorogoro instead of the bag), not just the
product as a whole. This is a **backend-only** change — no frontend files
touched. Unit picker on the Sell screen and a Repackage action screen are
still the open frontend work.

## What changed

**`apps/transactions/models.py`**
- `TransactionItem.product_unit` — new nullable FK to `catalog.ProductUnit`,
  `SET_NULL`. Null for every line that isn't a unit-specific sale (plain
  catalog sales, not-in-catalog items, stock-in, adjustments) — purely
  additive, no behaviour change for products that never set up a unit tree.
  `SET_NULL` rather than `PROTECT`/`CASCADE`: deleting a `ProductUnit`
  later must never delete or block deletion of historical sale rows — the
  item's own `quantity`/`unit_price`/`subtotal` already capture what was
  sold regardless of whether that specific form still exists.

**`apps/catalog/models.py`**
- `ProductUnit.restore_sale(quantity)` — new method, the mirror of the
  existing `deduct_sale()`. Adds back to whichever ancestor holds the
  counter for this pool. Needed once sales can happen against a unit —
  without it, voiding or refunding a unit-based sale would have restored
  stock to the wrong place (see below).

**`apps/transactions/serializers.py`**
- `TransactionItemCreateSerializer` — now accepts a third line-item shape,
  `{ product_unit_id, quantity }`, alongside the existing `{ product_id,
  quantity }` and `{ name, unit_price, quantity }` (not-in-catalog) shapes.
  The three are mutually exclusive — exactly one must be given. No
  `product_id` alongside `product_unit_id`: the product is derived from
  the unit itself in the view.
- `TransactionItemSerializer` (read shape) — added `product_unit` (id) and
  a computed `unit_label` (e.g. "Piece") so the frontend can show which
  form was actually sold on a receipt/history view without a second call.

**`apps/transactions/views.py`**
- `create_sale` — items carrying `product_unit_id` are resolved to a
  `ProductUnit`, scoped to the business, and checked against:
  - `is_sellable` (rejects selling a root/restock-only form)
  - `selling_price is not None` (a unit needs its own price before it can
    be sold — never derived as a fraction of the parent's price)
  - `available_quantity()` vs. requested quantity
  Passing validation, the price is taken from `unit.selling_price`, and
  stock is deducted via `ProductUnit.deduct_sale()` — which walks the
  chain to whichever ancestor actually holds the stock counter — instead
  of touching `Product.current_stock`. That's a deliberate, pre-existing
  separation: `Product.current_stock` and the `ProductUnit` tree's own
  counters are different pools (see the "Not built yet" note in the
  pre-pilot doc about a migration path for existing products to opt into
  multi-unit tracking — still open, untouched here). A dedicated
  `StockMovement` row is written per unit sale with `product_unit` set
  and `quantity_before`/`quantity_after` tracking the actual counted
  ancestor's pool, not the sold unit's own (unstored) quantity. No
  low-stock push fires for this branch — that notification is keyed off
  `Product.current_stock`/`low_stock_threshold`, neither of which this
  branch touches.
  Plain `product_id` sales and not-in-catalog items are **unchanged** —
  same code path, same behaviour, verified in the functional pass below.

- **`create_refund` and `void_transaction` — fixed, not just left alone.**
  Neither of these was in the original "not built yet" list, but adding
  unit-based sales without touching them would have been a real bug: both
  restore stock by adding back to `Product.current_stock`, which a
  unit-based sale never touched in the first place. Voiding or refunding
  a unit sale would have silently created phantom stock on `Product`
  while leaving the actual `ProductUnit` pool wrong forever. Both now
  branch on `item.product_unit_id` (or `original_item.product_unit_id`
  for refunds) and restore via `ProductUnit.restore_sale()` instead,
  with their own `REFUND`-type `StockMovement` row (`product_unit` set).
  Plain product-based void/refund is unchanged.
  Also widened both `prefetch_related` calls
  (`Transaction.objects.prefetch_related('items__product', ...)`) to
  include `'items__product_unit'`, so this doesn't reintroduce an N+1.

**`apps/core/messages.py`** — three new keys, English + Swahili:
  `PRODUCT_UNIT_NOT_SELLABLE`, `PRODUCT_UNIT_NO_SELLING_PRICE`,
  `PRODUCT_UNIT_INSUFFICIENT_STOCK`.

**`apps/transactions/migrations/0007_transactionitem_product_unit.py`**
  — new migration, hand-written rather than autogenerated. Its
  `dependencies` point at `0006_transaction_split_payment_amounts`
  explicitly — the documented live leaf of this app's migration chain —
  **not** at the stray duplicate
  `0004_transactionitem_is_reconciled_transactionitem_name_and_more.py`
  that's been sitting alongside `0004_phase9_unreconciled_items.py` since
  earlier work (see pre-pilot doc, Carried-over section). That duplicate
  is still unresolved and still deliberately untouched here — **run
  `python manage.py showmigrations transactions` against the real DB
  before running `makemigrations`/`migrate` there**, same caution as
  before. This migration was verified by temporarily merging locally
  (sqlite, throwaway) to prove it applies cleanly on top of both branches
  — that merge migration is *not* included in this delivery.

**Test-only, included for reference, not required in production:**
- `bizyangu/settings/testing.py` — sqlite in-memory settings + local-memory
  cache (no Postgres/Redis needed) for running the check below.
- `c10_sale_flow_check.py` — standalone functional pass via DRF's

## Verified (25/25 checks passed)

Against a real pack/stick tree (20 sticks per pack, 10 packs in stock):
- Selling sticks via `product_unit_id` deducts the *root* pool by the
  correct fraction (30 sticks → root drops by 1.5 packs), leaves
  `Product.current_stock` untouched, snapshots the unit's own price on
  the line item, and writes a `StockMovement` with the right
  before/after/delta against the pool that actually moved.
- Over-selling a unit (more than `available_quantity()`) is rejected
  with 400 and leaves stock unchanged.
- Selling a non-sellable unit (the root/restock form) is rejected.
- Selling a unit with no `selling_price` set is rejected.
- Sending both `product_id` and `product_unit_id` on one line is
  rejected (mutually exclusive shapes enforced).
- **Void** of a unit-based sale restores the root pool correctly and
  leaves `Product.current_stock` untouched — confirming the fix above,
  not just the new sale path.
- **Partial refund** (amount-only, apportioned) of a unit-based sale
  restores the correct fraction of the pool.
- A plain `product_id` sale (no unit tree involved) still deducts
  `Product.current_stock` exactly as before, with `product_unit` left
  null on the line — confirming full backward compatibility.

`manage.py check` and a full `makemigrations`/`migrate` pass (with the
temporary local merge described above) both ran clean.

## Not built in this pass (unchanged from the pre-pilot doc)

- Frontend: unit picker on Add Product, a Repackage action screen,
  sell-screen support for choosing which form to sell. This delivery
  only makes the API able to accept and correctly process a unit-based
  sale — the Sell screen still needs to actually offer that choice.
- A migration path for existing single-form products to opt into
  multi-unit tracking, and cost-price allocation down a repackaging
  chain — both still open, as before.
- The pre-existing duplicate `0004` migration in `transactions` — still
  not touched; needs a decision made against the real VM DB state, not a
  blind local merge.
