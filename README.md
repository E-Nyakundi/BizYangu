# C10 — Pack-to-unit selling: backend models, migrations, admin

This is the **models/migrations/admin layer only**, as agreed — no
serializers, API views, or frontend UI yet. The goal of this drop is
for you to check the shape in Django admin before I build anything on
top of it.

## What's in here

- `backend/apps/catalog/models.py` — two changes:
  1. `Product.Unit` — removed `DEBE_20L` entirely (a debe isn't a
     standard size; use Litre/Millilitre instead) and reworded
     `GOROGORO`'s label to drop the baked-in "~2kg" (gorogoro is a
     standard *volume* measure, not a standard weight — the weight
     depends on what's in it).
  2. New `ProductUnit` model — one sellable/stockable physical form of
     a product, tree-structured per product via `parent`. Each
     non-root node is either a shared stock pool with its parent (pack
     ↔ stick — exact, no event) or separately tracked and only
     populated via a `RepackageEvent` (bag → gorogoro — a real,
     lossy, loggable act). See the docstring in the file for the full
     reasoning — it's written to stand alone.
  3. `FIXED_UNIT_RATIOS` / `get_fixed_ratio()` — the handful of true
     unit-of-measure conversions (litre:ml = 1000, kg:g = 1000,
     dozen:piece = 12) that are safe to pre-fill as a default later,
     versus container-based ones (gorogoro, bag, pack) which always
     need the owner's real number.

- `backend/apps/inventory/models.py` — two changes:
  1. `StockMovement` gained a nullable `product_unit` FK and two new
     `MovementType` values (`REPACKAGE_OUT`/`REPACKAGE_IN`), so
     repackaging flows through the same existing audit trail your
     reports already read — no separate reporting path needed.
  2. New `RepackageEvent` model — the actual repackaging action.
     Validates that `to_unit.parent == from_unit` (you can't skip a
     level in a chain) and that `to_unit.is_repackaged` is set.
     Stores `expected_yield` and `loss_quantity` at creation time
     (not computed on read), so editing a ratio later doesn't
     retroactively change historical loss figures.

- `backend/apps/catalog/migrations/0006_...py` and
  `backend/apps/inventory/migrations/0002_...py` — real migrations,
  generated by actually running `makemigrations` against a throwaway
  sqlite DB with your real models loaded (not hand-written), and
  verified to apply cleanly end-to-end from a blank database in that
  same sandbox.

- `backend/apps/catalog/admin.py` / `backend/apps/inventory/admin.py`
  — `ProductUnit` registered standalone and as an inline on `Product`
  (so you can see one product's whole unit tree at a glance);
  `RepackageEvent` and `StockMovement` registered (inventory had no
  admin.py at all before this).

- `frontend/lib/knowledge.ts` and `knowledge/units.json` — removed
  `debe_20l` and reworded the gorogoro label in both, to stay in sync
  with the backend enum (the code comment in `models.py` specifically
  warns these three lists drifting apart causes silent 400s — same
  landmine as the one already documented in migration 0002).

## Tested before packaging

Actually ran, not just read:
- `python manage.py makemigrations` — generated the two migration
  files above from the real model diff, not hand-authored.
- `python manage.py migrate` from a blank sqlite DB — every migration
  in the project applies cleanly in order, including these two.
- `python manage.py check` — no issues.
- A Django shell script exercising all three of your original
  examples directly against the models:
  - Cigarettes (pack/stick, shared pool): sold 3 sticks, pack stock
    correctly dropped by 0.15 packs, remaining stick count correct.
  - Maize (bag → gorogoro): repackaged 1 bag into 44 tins (against a
    45-tin theoretical yield), loss correctly computed as 1, tins
    available for sale only after the repackage event, bag stock
    correctly decremented by exactly 1.
  - Cooking oil: confirmed `get_fixed_ratio(LITRE, MILLILITRE) == 1000`
    and confirmed gorogoro↔kg correctly returns `None` (no unsafe
    default for a container-based conversion).
  - Chain: bag → gorogoro → sachet, two repackage events, loss
    tracked independently at each level.
  - Guardrail: attempted a repackage from bag directly to sachet
    (skipping the gorogoro level) — correctly rejected with a
    validation error.

None of that means it's bug-free against your real Postgres data or
real usage patterns — it means the logic does what we designed it to
do, in isolation, against a clean DB.

## How to apply

1. Copy these files into your project at the same relative paths,
   overwriting the originals.
2. `python manage.py makemigrations --check` first if you want to
   confirm nothing else in your local tree has drifted and would
   produce an unexpected extra migration.
3. `python manage.py migrate`.
4. Check Django admin — create a test product, add a couple of
   `ProductUnit` rows via the inline, confirm the tree looks right.

## Not built yet — next steps

- Serializers + API views for `ProductUnit`/`RepackageEvent` (create,
  list, the actual sell/repackage endpoints).
- Frontend: unit-picker UI on Add Product, a "Repackage" action screen,
  and the sell screen needs to let a cashier choose which sellable
  form of a product they're selling.
- Existing products need a migration path — right now every existing
  `Product` has no `ProductUnit` rows at all, which is fine (they keep
  working exactly as before via `Product.current_stock`), but there's
  no UI yet for an owner to opt an existing product *into* multi-unit
  tracking.
- Cost-price allocation down a chain (what a single gorogoro "costs"
  once the bag's cost is known) is deliberately not addressed here —
  flagged as a later decision, not forgotten.
